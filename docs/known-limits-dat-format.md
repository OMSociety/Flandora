# 图片 .dat 封装：结构与判定（已知明文实证）

> 微信 4.1.15.56 / Windows。本文只写实测事实。

## 零、关键材料

| 材料 | 来源 | 大小 |
|---|---|---|
| 明文 A | 微信解码落盘目录 `temp\RWTemp\<日期>\<会话>\<md5>.jpg` | 59964 B |
| 明文 B | 用户在微信里「另存为」导出的同一张图 | 59964 B |
| 密文 | 消息附件目录 `msg\attach\<会话>\<日期>\Img\<md5>_t.dat` | 61019 B |

明文 A 与明文 B 逐字节完全相同，确认是同一张图；密文的 `xor_size` 恰为 59964。

## 一、文件结构（确证）

| 偏移 | 长度 | 内容 | 实测 |
|---|---|---|---|
| 0 | 6 | magic | `07 08 56 32 08 07` |
| 6 | 4 | 段 1 明文长度（u32 LE） | 恒为 1024；密文按 PKCS#7 补齐到 16 的整数倍，故恒为 1040 |
| 10 | 4 | 段 2 长度（u32 LE） | 恒为 `文件长度 - 1055` |
| 14 | 1 | 标志 | `01` |
| 15 | 1024 | 段 1 | 密文，熵 7.94 |
| 1039 | 16 | 段 1 的 PKCS#7 填充块 | 密文；每个账号固定，见下 |
| 1055 | `段2长度` | 段 2 | 密文，熵 7.97 |

61019 = 15 + 1024 + 16 + 59964，与明文长度严丝合缝。

[1039:1055] 那 16 字节**不是明文中段**，而是段 1 明文按 PKCS#7 补齐后多出来的那一块
（明文长度整除 16 时，PKCS#7 仍要补满一整块）。它看起来像「按账号不同的常量」，
是因为同一账号同一密钥下，ECB 加密固定填充块得到的结果不变。把它当明文拼回载荷，
JPEG / PNG 只是画面上多一道花，HEVC（`wxgf`）那类比特流会从这里失步——CABAC 没有
重同步点，整张图只剩上面一小条能解。

段 1 填充块的密文：

| 账号 | `[1039:1055]` |
|---|---|
| 账号 A | `e935effe8aa238bec419c3ecf8f3705c` |
| 账号 B | `54e680384c587266da2e5e6841747a23` |

## 二、微信实际读取的是哪一份

钩 `CreateFileW` 实测：打开聊天图片时，微信读的是

```
cache\<日期>\Message\<会话>\Bubble\<md5>_b.dat
```

而不是 `msg\attach\...\Img\*.dat`。两者是同一 V2 格式、段 1 字节完全相同，
`Bubble` 那份更大，是显示用的版本。

**实测得出的一条关键规律**：删掉某会话的 `cache` 目录并重启微信后，该会话的
图片变成空白，且不会自动恢复——说明图片显示完全依赖 cache，cache 由解码产出。
删掉后再次触发该会话，微信会重新生成：

```
cache\...\Message\<会话>\Thumb\<key>_thumb.jpg    明文 JPEG
cache\...\Message\<会话>\Bubble\<key>_b.dat       密文 V2
```

两者文件名前缀相同、生成时间相差 1 秒内，是**同一张图的两个形态**，构成一组
可用的已知明文 / 密文配对。

## 三、用这组配对得到的判定

以 `397_1792759710` 为例：

| 项 | 值 |
|---|---|
| 明文（Thumb） | 32605 B，JPEG，熵 7.953 |
| 密文（Bubble）段 2 | 180848 B，熵 7.965 |
| 段 2 与明文长度差 | +148243 B |

在段 2 里按 16 字节步长扫描每个起点，把该处起 256 字节与明文开头异或，
最小唯一值 136/256；尾部对齐 161/256；段 1 对明文头/尾分别 150/256、152/256。
**全部处于随机水平**（真正对齐时应接近 1）。

第二组 `422_1792766827` 结果相同（135/256、157/256、148/256、170/256）。

结论：**密文与这份明文缩略图之间不存在可判定的位置对应**。

补充（后续查明）：这条结论本身成立，但它**不能推出「段 2 不是图像」**——当时拿来
比对的 `Thumb` 是缩略图，而段 2 承载的是全尺寸图像，两者内容本就不同，异或自然停在
随机水平。真相比这简单：段 1 是 AES-128-ECB 密文，解密后**就是图像的开头**；段 2 是
XOR 段，接在明文常量之后。完整图像由「段 1 解密 + 明文常量 + 段 2 解密」拼成。详见
§七。

## 四、段 1 是共享的元数据

- `Bubble` 的 48 个样本里，段 1 共 12 种取值，其中一种重复 **37 次**；
- 397 与 422 两个不同文件的段 1 **前 24 字节完全相同**
  （`4bf256a858725f8f9f2c7084a74a58f4…`），整段不同；
- 段 1 熵 7.94–7.99，无恒定字节、无可读文本。

即：段 1 = 固定文件头 + 每文件专属字段，仍是密文。

## 五、另一组长度相等的配对（59964 B）

另有一组明文与密文长度恰好相等（都是 59964 B），做全偏移比对：

| 检验 | 结果 |
|---|---|
| `tail == plain` | 否 |
| `tail[i] == plain[i]`（偏移 −64…+64 全扫） | 0.32%–0.41%，随机水平 |
| `tail = plain XOR 单字节` | 无解 |
| `tail = plain XOR 周期密钥流`（P = 2…1024） | 全部在第 2~1024 字节冲突 |
| 长度 24 字节以上的共享片段 | 零 |
| 字节频率分布的 Pearson 相关 | r = 0.0032 |

（这一组比对的「密文」是文件尾段，「明文」是整张图。按 §七 的结构，尾段只是整图
的最后一截而非全部，所以「尾段 = 整图 XOR 单字节」本来就不该成立——它不与 §七 的
「尾段 XOR 单字节密钥」矛盾。真正成立的是「尾段 = 整图尾段 XOR 单字节」。）

## 六、已否证的取钥路径

下表是**取 AES 密钥**这条线上被排除掉的路（密钥最终由内存扫描在解码时取到，见 §七）。
排除它们的主要收获是指出了方向：密钥不在任何持久化数据里，只在使用时存在于内存。

| 路径 | 结果 |
|---|---|
| 消息库 XML 的 `aeskey` / `cdnthumbaeskey`（67 个 × 三种形态） | 全否 |
| 进程内存 ASCII 候选（5 进程约 30 万个） | 全否 |
| 明文常量邻域 ±0x400 的二进制窗口 | 全否 |
| 38 个已解密库中的 54695 个候选 | 全否 |
| md5/sha1/sha256/sha512 派生（113 组，含 V1 的 `md5("0")`） | 全否 |
| Hook CNG `BCryptDecrypt` / `BCryptGenerateSymmetricKey` | 微信走 AES-NI，零调用 |
| Hook AES-NI 密钥扩展（205 次调用，252 候选） | 全否 |
| Hook AES-NI 解密（2302 次调用，2893 候选） | 全否（命中 TLS：出现 878 次的测试向量 `000102...0f`） |
| `key_info.dat`（登录时刷新的 180 字节文件）当口令/密钥 | 全否 |
| 全盘按 `xor_size == 明文长度` 配对 | 只有 1 组 |

## 七、还原方式（已实现）

两个密钥都已取到，图片消息不再落成占位符。

| 密钥 | 值 | 性质 | 取法 |
|---|---|---|---|
| AES | 16 字节 | 按账号，同一账号所有图片共用一把 | 微信解码图片的那几秒里扫进程内存 |
| XOR | 单字节 | 按账号 | 由文件尾反推（JPEG 末两字节必为 `FF D9`） |

还原过程：

```
明文 = AES-128-ECB-解密(段 1)‖明文常量(16B)‖(段 2 XOR 单字节密钥)
```

**取 AES 密钥的关键是时机，不是位置**：它只在微信真正解码某张图片的那几秒驻留内存，
登录后静止状态下扫不到。可行做法是删掉目标会话的 `cache` 目录、重启微信、再打开该
会话触发解码，同时以秒级间隔反复扫描。`tools/imagekey.py` 就是这个流程的封装。

已知边界：

- 密钥**按账号**，换号后要重取（与库口令同理，代码里按当前账号校验，不一致时按
  「无密钥」处理并提示重取）。
- 需要目标账号的密钥；手上没有第二个号，因此没有做过跨账号的对照验证。
- 语音与文件同为加密 `.dat`，**未还原**。
- `wxgf` 是微信私有的 HEVC 容器，本程序不解析它，改用微信自己留在旁边的明文副本：
  `<md5>_h.dat`（高清原图）> `cache/**/Bubble/<md5>_b.dat`（预览）> `<md5>_t.dat`
  （缩略图）。一份都没有时按「图片取不到」处理，退回 `[图片]` 占位。

实现与验证证据：

| 项 | 结果 |
|---|---|
| 账号 A 全量 | 全部解码成功（`flandora/wx_image.py` 记录 195/195） |
| 端到端 | 285 条消息 / 21 张图片 / 21 条带路径 |
| 格式分布 | jpg 78 / png 75 / wxgf 16 |
| wxgf 取图（2026-10-26 复核，94 张主图） | 全部取件成功：43 张主文件本身即 jpg/png、15 张挑到 `_h`、36 张挑到 `_b`；0 失败 |
| 抽样 | 4080×3072、3072×4096、210×467 等均可正常打开 |
| 单测 | `tests/test_wx_image.py` 10/10、`tests/test_wx_store_images.py` 6/6、`tests/test_image_key_owner.py` 3/3 |

## 八、仍未知的部分

- 那个按账号不同的 16 字节常量（`[1039:1055]`）是什么，未查明。
- AES 密钥**为什么**是这个值、微信从哪里取得它，未查明——本方案只是把它从内存里
  取出来，不解释它的来历。这意味着微信升级后取法可能需要调整（密钥仍会驻留内存，
  但「几秒窗口」这个特征是否保持，未验证）。
- 段 1 的长度恒为 1024 是实测事实，原因未查明。
