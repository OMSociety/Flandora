# 图片 .dat 封装：结构与判定（已知明文实证）

> 微信 4.1.15.56 / Windows。本文只写实测事实。

## 零、这一轮拿到的关键材料

| 材料 | 来源 | 大小 |
|---|---|---|
| 明文 A | 微信解码落盘目录 `temp\RWTemp\<日期>\<会话>\<md5>.jpg` | 59964 B |
| 明文 B | 用户在微信里「另存为」导出的同一张图 | 59964 B |
| 密文 | 消息附件目录 `msg\attach\<会话>\<日期>\Img\<md5>_t.dat` | 61019 B |

**明文 A 与明文 B 逐字节完全相同**（`a == b` 为 True），确认是同一张图。
密文的 `xor_size` 恰为 59964，与明文长度相等，这是目前唯一一组对得上的配对。

## 一、文件结构（确证）

| 偏移 | 长度 | 内容 | 实测 |
|---|---|---|---|
| 0 | 6 | magic | `07 08 56 32 08 07` |
| 6 | 4 | AES 段长度（u32 LE） | 恒为 1024 |
| 10 | 4 | 尾段长度（u32 LE） | 恒为 `文件长度 - 1055` |
| 14 | 1 | 标志 | `01` |
| 15 | 1024 | AES-128-ECB 段 | 密钥未取得 |
| 1039 | 16 | 明文常量 | 按账号不同 |
| 1055 | `xor_size` | 尾段 | 见 §2 |

61019 = 15 + 1024 + 16 + 59964，与明文长度严丝合缝。

按账号不同的常量：

| 账号 | 常量 `[1039:1055]` |
|---|---|
| 账号 A | `e935effe8aa238bec419c3ecf8f3705c` |
| 账号 B | `54e680384c587266da2e5e6841747a23` |

## 二、尾段与明文的实测关系

### 2.1 不是任何简单变换

| 检验 | 结果 |
|---|---|
| `tail == plain` | 否 |
| `tail[i] == plain[i]`（偏移 −64…+64 全扫） | 0.32%–0.41%，随机水平 |
| `tail = plain XOR 单字节` | 无解 |
| `tail = plain XOR 周期密钥流`（P = 2…1024） | 全部在第 2~1024 字节就冲突 |
| 长度 24 字节以上的共享片段 | 零 |
| 字节频率分布的 Pearson 相关 | r = 0.0032（无关） |

### 2.2 但存在一个真实的统计相关

明文取值 `0x00` 的位置上，`tail` 有 242 次是 `0x6a`、110 次是 `0x2e`。

| 项 | 值 |
|---|---|
| 明文 0 的个数 | 1221 |
| tail 中 0x6a 的个数 | 1724 |
| 若独立，期望交叉数 | 35.1 |
| 实测交叉数 | 352 |
| **卡方贡献** | **1219.4**（p ≪ 0.001） |

这个相关是真的，但它不来自逐字节映射——因为同一位置在别处 `plain=0x00` 时
`tail` 又是别的值（映射不唯一）。

### 2.3 解释：尾段是「低熵图案 + 高熵数据」的混合

按位置 mod 3 分组，各组的最高频值恰为 `0x2e / 0x6a / 0x6a`，也就是 `2e 6a 6a`
这个周期图案。但该图案只覆盖 **1902 / 59964 = 3.17%** 的位置，其余 96.83% 是
高熵数据（熵 7.968）。

`0x2e` 的出现间隔**恒定为 3**（409 次），`0x6a` 的间隔是 1 和 2 交替——这是
周期结构留下的指纹。明文里大量 `0x00` 落在这些周期位置上，于是产生了 §2.2 的
相关性。

结论：尾段里确实混有周期性填充，但承载图像的绝大多数字节与明文没有可判定的
逐字节关系。

## 三、1024 字节段确实是 AES-ECB 密文

两个独立证据：

1. **重复段**：不同图片的 1024 字节段存在完全相同的副本（账号 A 的 60 个样本里 8 组重复，账号 B 4 组）。ECB 模式下相同密文块只能来自相同明文块，说明这
   一段是**元数据模板**，多张图共用。
2. **位置级重合**：逐位置统计 40 个样本，某些位置出现完全相同的 8 字节片段
   （如账号 A 的 `[0x000:0x008]` 只有 15 种取值、`[0x020:0x028]` 只有 9 种）。

段内熵 7.941–7.994，无恒定字节，无可读文本。

## 四、抓不到密钥的原因（已查明）

在 AES-NI 路径上做了两轮挂钩，都没抓到：

| 挂钩点 | 方式 | 结果 |
|---|---|---|
| 密钥扩展（AESKEYGENASSIST，RVA `0x5a24720`） | 动态扫描定位，唯一函数 | 205 次调用，252 个候选，全否 |
| AES 解密（AESDEC，4 个函数） | 4 个函数全挂，每调用采 16 个参数位 | 2302 次调用，2893 个候选，全否 |

**这些命中全部是网络层 TLS，不是图片解密。** 判据：出现次数最高的候选是
`000102030405060708090a0b0c0d0e0f`（878 次）——这是公开的测试向量，也是 TLS
握手常用的预置密钥；另有大量 `00000000000000000000000000000000`（562 次）。

配合另一个实测：点开一张**已缓存**的图片后，沙箱里没有任何图片文件被写出，说明
微信把解码结果留在内存里，不会重新读 `.dat`。所以「在解密时抓 key」这条路，需要
的是一次真正的磁盘读取（清缓存后首次打开），而不是点开已缓存的图。

## 五、已否证的取钥路径

| 路径 | 结果 |
|---|---|
| 消息库 XML 的 `aeskey` / `cdnthumbaeskey`（67 个 × 三种形态） | 全否 |
| 进程内存 ASCII 候选（5 进程约 30 万个） | 全否 |
| 明文常量邻域 ±0x400 的二进制窗口 | 全否 |
| 38 个已解密库中的 54695 个候选 | 全否 |
| md5/sha1/sha256/sha512 派生（113 组，含 V1 的 `md5("0")`） | 全否 |
| Hook CNG `BCryptDecrypt` / `BCryptGenerateSymmetricKey` | 微信走 AES-NI，零调用 |
| Hook AES-NI 密钥扩展（205 次） | 全否 |
| Hook AES-NI 解密（2302 次） | 全否，命中的是 TLS |
| 全盘按 `xor_size == 明文长度` 配对 | 只有 1 组 |

## 六、结论

图片这一项按发布阻塞处理。要再往前一步，下一条路是**清掉某张图的缓存后重新
打开**，让微信真的从磁盘读一次 `.dat`，同时挂着 AESDEC 钩子——那时抓到的才可能
是图片密钥。这一条还没有试过。
