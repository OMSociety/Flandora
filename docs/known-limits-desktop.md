# 发送通道与前台：为什么向微信投递输入会抢前台，以及隔离桌面为什么能解决

> 微信 4.1.15.56 / Windows 11。本文只写实测事实；纯结构推论单独标注。

## 一、结论

**在同一个桌面内，「消息发得出去」与「微信不升到前台」互斥。**

向微信进程投递任何形式的输入——鼠标消息、键盘消息、`SendMessage`、UIA 的
`SetFocus()` / `SetValue()`、乃至 `SetActiveWindow()` 本身——都会使微信窗口成为
前台窗口。不投递输入就没有输入到达微信，消息也就发不出去。

这条约束不能靠调整投递方式绕开（§2 逐个试过）。但「抢前台」是**桌面局部**的：
每个 Windows Desktop 有自己的前台窗口。把微信放到另一张桌面上，它升到前台只
影响那张桌面，用户所在的 Default 桌面不受影响（§4）。这就是 `isolated_desktop`
选项的实现依据。

## 二、逐机制否证（13 项）

统一条件：先把一个非微信窗口提到前台并确认它确实是前台，再执行被测动作，动作后
立即用 `GetForegroundWindow()` 判定。

| # | 被测动作 | 输入是否到达微信 | 微信是否升到前台 |
|---|---|---|---|
| 1 | 点输入框（全程不 `AttachThreadInput`） | 到达 | 是 |
| 2 | 附着微信线程后点输入框 | 到达 | 是 |
| 3 | 不点击、不附着，直接投 `WM_CHAR` | 到达 | 是（重复 3 次，每次都抢） |
| 4 | 用 `SendMessageTimeoutW` 投 `WM_CHAR` | 到达 | 是 |
| 5 | UIA `SetFocus()` 给输入框 | 输入框获得焦点 | 是 |
| 6 | 向渲染子窗投 `WM_SETFOCUS` | 未改变焦点 | 否；但紧随其后的 `WM_CHAR` 仍然抢 |
| 7 | `AttachThreadInput` + `SetActiveWindow(微信)` | 本模式不投输入 | 是 |
| 8 | 早期文档记录的完整配方（含 `SetActiveWindow`） | 到达 | 是 |
| 9 | UIA `ValuePattern.SetValue()` 写入输入框 | 到达 | 是 |
| 10 | UIA 发送按钮 `LegacyIAccessiblePattern.DoDefaultAction()` | 消息实际发出 | 是 |
| 11 | 输入框没有键盘焦点时投 `WM_CHAR` | 到达 | 是 |
| 12 | `PostMessage` Shift 按下 / 抬起 | 到达 | 是（3/3） |
| 13 | `SetForegroundWindow(微信)` | — | 是（3/3） |

反向对照（**不会**触发抢前台）：`PostMessage WM_MOUSEMOVE`（0/3）、UIA
`SetFocus()` 本身（0/3，但后续输入仍会抢）、`BringWindowToTop`（0/3）。

即：**投递键盘类消息会触发，纯鼠标移动与窗口层级调用不会**。

第 9、10 两项合起来是一条完全不依赖打字的发送路径，实测能发出消息，但两步都抢
前台——所以「换一种投递方式」不是出路。

## 三、一条踩过的坑：采样点错位会漏检副作用

早期验证脚本判定为「全程未被抢前台」，复现同一路径得到的是「是」。差异不在配方，
而在**判定采样点**：早期脚本把「动作前的前台」采样点放在了取得输入框焦点之后、
投递动作之前，于是抢前台那一步已经发生完毕，采样到的「前」和「后」都是微信，判定
为「未变」。

修正采样点（动作前在受害者被提到前台之后立刻取一次）后，同一条路径每次都检出抢前台。

教训：验证「某动作没有引起副作用」时，基准采样点必须在副作用可能发生之前的最后一
次外部干扰之后取。

## 四、隔离桌面：实测与代价

用 `CreateDesktopW` 造独立桌面，用 `STARTUPINFO.lpDesktop` 在其上启动微信。

成立的部分：

| 检查项 | 结果 |
|---|---|
| 微信能否落在隔离桌面 | 能，`EnumDesktopWindows` 看得到它的窗口 |
| 是否漏到 Default 桌面 | 否，Default 上 0 个新窗口 |
| 向隔离桌面上的微信投 `WM_CHAR` | **Default 前台不变** |
| UIA 能否跨桌面访问 | 能，`ControlFromHandle` 拿得到控件树 |
| 截图 | `PrintWindow` 成功；`BitBlt` 失败（返回全 0） |
| 点击 | `PostMessage` 投鼠标消息有效；UIA `InvokePattern.Invoke()` 无效（Qt 在窗口未激活时不响应） |

代价：

1. **微信必须由本程序启动。** Windows 上微信单实例互斥：Default 桌面上已有微信时，
   隔离实例只停到登录页。
2. **隔离桌面用户看不见，首次登录要靠截图。** 本程序把微信窗口画面实时显示在 面板
   的「微信画面」页，用户在那里点「登录」，再按提示用手机扫码或确认。实测该界面文案
   为「需在手机上完成登录」。
3. **微信不显示在用户屏幕上**——这正是该模式的目的，但它意味着这种模式下用户平时
   看不到自己的微信。
4. **每次重启桥接都要重新登录一次微信。** 隔离桌面随桥接进程一起销毁，其上的微信进程
   也一并结束。重启后微信停在登录页，用户要在「微信画面」页重新登录（实测三轮重启
   都是如此）。

因为代价 1、3，该模式做成配置项 `isolated_desktop`，默认关闭。关闭时保持原行为：
发送时微信短暂到前台，每个投递动作后立即把前台还给原窗口（实测文本 0 ms、图片
40 ms 以内；归还手法 3/3 成功，偶尔还不上时记一条日志说明目标窗口是否还在）。
开启时不还前台：那张桌面上只有微信一个窗口、没人看，没有「被占住的前台」要还，
还不上时还要白等 1 秒轮询。

该模式还有一条硬前提：与微信打交道的那条线程必须先 `SetThreadDesktop` 归位到微信
所在的桌面。修饰键状态只共享给同桌面的线程，`AttachThreadInput` 也要求两个线程在
同一张桌面；不归位时附着失败，`Ctrl+V` 会在输入框里留下字面的 `v`，靠剪贴板投递的
正文、图片、文件全都发不出去（实测）。

## 五、仍然成立、可继续使用的控件事实（微信 4.1.15.56）

| 控件 | 类名 | 说明 |
|---|---|---|
| 会话列表 | `mmui::ChatSessionList` | 会话项 `mmui::ChatSessionCell`，高约 109 像素 |
| 会话项文本 | — | `Name` 为多行：第 1 行会话名，第 2 行最后一条消息摘要，第 3 行时间 |
| 输入框 | `mmui::ChatInputField` | 外层 `mmui::XValidatorTextEdit`；`ValuePattern.Value` 为已输入文本 |
| 搜索入口 | `mmui::XSearchField` | 点击后焦点转到子控件 `mmui::XValidatorTextEdit` |
| 搜索弹层 | `mmui::SearchContentPopover` | **独立顶层窗口**，类名 `Qt51514QWindowToolSaveBits` |
| 搜索结果项 | `mmui::XTableCell` | 同名结果不止一个（「功能」分区下还有动作项） |
| 发送按钮 | `mmui::XOutlineButton` | `Name` 为「发送」，`DoDefaultAction()` 能发出消息 |

两个用于状态判定的类名：登录窗与主窗的 **Win32 类名都是 `Qt51514QWindowIcon`**，
只能靠 UIA 的 `ClassName`（`mmui::LoginWindow` / `mmui::MainWindow`）区分。按 Win32
类名判断会把登录界面误认成主界面。微信掉线后登录布局也承载在 `mmui::MainWindow`
里，所以判定还要看窗口内容而不是只看类名。

会话项 `Name` 的第 2 行是**可用的发送确认通道**：发完后读该行的摘要就能判断消息是否
真的落到会话里，不需要读数据库。

## 六、一个会毁掉整个通道的故障模式

**在搜索弹层不存在时给它发 `Esc`，微信会把整个主界面收进托盘。** 托盘化后再用
`ShowWindow` 恢复显示，UIA 无障碍树不会重建——只剩 `mmui::MainWindow` 与其渲染子窗
两级（约 2 个节点），任何控件都找不到，且等待不会恢复，必须重启微信。

判据：主窗存在且 `IsWindowVisible` 为真，但 UIA 树节点数不超过 4，即判定无障碍树已
失效。`uia_sender.py` 的 `_find_window()` 已加入该判据并在绑定时直接失败。

关闭弹层前必须先确认弹层存在（`mmui::SearchContentPopover` 是否在树里），不能无条件
发 `Esc`。

## 七、一组操作要点

1. **输入框必须先获得 Qt 内部焦点**，之后 `WM_CHAR` 才落得进去；点击输入框是取得该
   焦点的手段（也是抢前台的那一步）。输入框是否持有 Windows 键盘焦点与能否接收
   `WM_CHAR` 无关。
2. **搜索弹层必须按它自己的 HWND 投递。** 它虽然作为 `mmui::MainWindow` 的子节点出现
   在 UIA 树里，鼠标消息投给主窗到不了弹层，症状是「打字能出结果、点了却切不过去」。
   客户坐标也要按弹层的 HWND 计算。
3. **重复点击当前会话行会清空聊天面板**（UIA 树从约 157 节点掉到约 80 节点）。切会话
   前先用输入框 `Name` 判断当前会话，相同则跳过点击。
4. **输入法会扰动字符**（实测 `t` 变成 `上`）。写字后必须回读输入框
   `ValuePattern.Value` 校验，不符则清空重打。
5. `AttachThreadInput` 期间两个线程共用输入队列，用完立即解除，不要长持。

## 八、未做的判别实验

微信是**自己**激活自己（对 `WM_MOUSEACTIVATE` 返回 `MA_ACTIVATE`，或 Qt 在焦点变化时
调用 `SetForegroundWindow`），还是 Windows 对后台进程的输入投递本身带有激活语义——
本轮没有做区分实验，**两种解释都未定论**。

外部观测中有一条更偏向后者的证据：只做 `AttachThreadInput` + `SetActiveWindow`、
不投任何输入就抢到了前台。但不足以定论。判别方法是在微信进程内挂钩
`SetForegroundWindow` / `SetWindowPos`，观察调用是否由微信自身发起。

无论哪一种，对本项目的结果相同：发送必须投递输入，投递输入必然激活微信。
